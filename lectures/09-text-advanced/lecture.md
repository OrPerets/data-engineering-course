# Text Analytics for Industrial Engineering & Management

## 1. Why Text Analytics Matters for IEM (operations framing)
Text is a **process output**: customer complaints, service tickets, maintenance logs, supplier notes, and HR feedback are signals generated by operational systems. The goal is not “NLP.” The goal is **better decisions**: prioritize issues, reduce queue backlog, detect rare but critical failure modes, and feed dashboards with measurable KPIs.

**Managerial framing:**
- Text fields are **workload indicators** (what people are writing about most).
- Rare phrases often signal **high cost, high risk** issues.
- We need **repeatable metrics** (versioned tokenization, stable vocabularies) so trends are real, not artifacts.

> **What should a manager care about here?**
> - Are we surfacing the *right* issues from thousands of notes?
> - Are our metrics stable enough to support weekly reviews?

> **When is this overkill?**
> - When volume is small (<500 texts/week) and manual review is cheaper.

> **What metric tells us something is broken?**
> - Sudden jumps in vocabulary size, OOV rate, or reducer max/median load ratio.

## 2. Rewritten Week: TF-IDF (operations + analytics)

### 2.1 Intuition (Operational)
TF‑IDF highlights **terms that are common in one document but rare across the system**. In IEM terms, that means **locally frequent + globally rare = likely important**. We treat each ticket/report as a document and each token as a process signal.

### 2.2 Math (with interpretation)
\[
\text{tf}(t,d) = \frac{f_{t,d}}{|d|}
\]
**Interpretation:** the share of a document devoted to term *t*; larger = more attention spent on that issue in that record.

\[
\text{idf}(t) = \log\left(\frac{N+1}{df(t)+1}\right)
\]
**Interpretation:** penalty for being common across all records; rare terms get higher weight.

\[
\text{tfidf}(t,d) = \text{tf}(t,d) \times \text{idf}(t)
\]
**Interpretation:** a composite score that flags **locally dominant + globally rare** signals.

### 2.3 SQL‑Lens for TF‑IDF (why SQL strains)
- **TF (per document)**
  - *SQL idea:* `GROUP BY doc_id, term` to count tokens, then divide by doc length.
  - *Why SQL strains:* token explosion -> massive GROUP BY + joins to doc length.

- **DF (global per term)**
  - *SQL idea:* `COUNT(DISTINCT doc_id)` per term.
  - *Why SQL strains:* high‑cardinality distinct counts; skew from stop-words.

- **TF‑IDF**
  - *SQL idea:* join TF table with DF table, compute formula.
  - *Why SQL strains:* huge join between per-doc and global stats.

**Pseudo‑SQL snippet (conceptual):**
```
-- TF table
SELECT doc_id, term, COUNT(*)/doc_len AS tf
FROM tokens
GROUP BY doc_id, term;

-- DF table
SELECT term, COUNT(DISTINCT doc_id) AS df
FROM tokens
GROUP BY term;

-- TF-IDF join
SELECT t.doc_id, t.term, t.tf * LOG((N+1)/(d.df+1)) AS tfidf
FROM tf_table t
JOIN df_table d USING(term);
```

### 2.4 Operational risks (TF‑IDF)
- **Stop‑word skew:** “the”, “and” overload one reducer → stragglers, cost spikes.
- **Vocabulary explosion:** IDs, typos, URLs inflate memory and I/O.
- **Reproducibility risk:** changing tokenization shifts metrics; trend charts become meaningless.

> **What should a manager care about here?**
> - Is the backlog triage based on stable TF‑IDF signals?

> **When is this overkill?**
> - If the goal is only basic keyword counts; TF‑IDF adds compute cost.

> **What metric tells us something is broken?**
> - Max/median reducer load ratio; vocabulary size trend; % dropped tokens.

## 3. Rewritten Week: Advanced Text (n‑grams, regex, embeddings)

### 3.1 N‑grams = short phrases as signals
**Why:** single words miss context (e.g., “not working”). N‑grams capture local order without full sequence modeling.

**Growth intuition:** If vocabulary size is \(V\), potential n‑grams are up to \(V^n\). **Interpretation:** each increase in *n* multiplies feature space and storage cost.

**SQL‑lens:**
- *What it looks like:* generate token windows and `GROUP BY doc_id, ngram`.
- *Why SQL strains:* window generation is heavy; feature count explodes.

**Operational hazard:** common phrases (“call back”, “asap”) can create **hot keys** in global DF stage.

> **What should a manager care about here?**
> - Does adding bigrams improve issue categorization enough to justify cost?

> **When is this overkill?**
> - When unigram TF‑IDF already separates issues clearly.

> **What metric tells us something is broken?**
> - N‑gram vocabulary growth rate; reducer skew in DF job.

### 3.2 Regex = cleaning + extraction, but a risk
Regex is powerful for cleaning dates, IDs, or error codes—but **unsafe patterns can stall pipelines**.

**SQL‑lens:**
- *What it looks like:* `REGEXP_EXTRACT` or `REGEXP_REPLACE` in a SELECT.
- *Why SQL strains:* catastrophic backtracking creates long‑running tasks and cluster timeouts.

**Operational hazard:** one pathological record can stall an entire batch.

> **What should a manager care about here?**
> - Are regex failures delaying daily dashboards?

> **When is this overkill?**
> - When simple tokenization + dictionary lookup suffices.

> **What metric tells us something is broken?**
> - Regex timeout rate; task duration outliers.

### 3.3 Embeddings = compressed signals
Embeddings map tokens to dense vectors (e.g., 100‑dim). They **compress meaning** into fixed space.

**SQL‑lens:**
- *What it looks like:* join token table with embedding table.
- *Why SQL strains:* high‑dimensional arrays; heavy joins; version management.

**Operational hazard:** OOV (out‑of‑vocabulary) tokens degrade quality; versions drift over time.

> **What should a manager care about here?**
> - Is the OOV rate stable? If not, system signals are drifting.

> **When is this overkill?**
> - If the decision problem is simple prioritization, TF‑IDF may suffice.

> **What metric tells us something is broken?**
> - OOV rate spikes; embedding version mismatch counts.

## 4. Worked Example Bank (all calculations together)
Each example uses a small table, tokenization, TF, DF, IDF, and TF‑IDF. **High TF‑IDF = managerial importance** because it flags **locally emphasized + globally rare** issues.

### Example 1: Service Tickets (simple triage)
**Table:**
| ticket_id | text | department |
|---|---|---|
| T1 | "printer jam jam" | Facilities |
| T2 | "printer offline" | Facilities |
| T3 | "vpn outage" | IT |
| T4 | "vpn slow" | IT |
| T5 | "printer jam" | Facilities |

**Tokenization:**
- T1: printer, jam, jam (len=3)
- T2: printer, offline (len=2)
- T3: vpn, outage (len=2)
- T4: vpn, slow (len=2)
- T5: printer, jam (len=2)

**TF (selected):**
- tf(jam, T1) = 2/3 = 0.67
- tf(offline, T2) = 1/2 = 0.50
- tf(outage, T3) = 1/2 = 0.50

**DF:**
- df(jam)=2 (T1,T5)
- df(offline)=1 (T2)
- df(outage)=1 (T3)
- N=5

**IDF:**
- idf(jam)=log((5+1)/(2+1))=log(2)=0.69
- idf(offline)=log(6/2)=log(3)=1.10
- idf(outage)=log(6/2)=1.10

**TF‑IDF:**
- tfidf(jam,T1)=0.67*0.69=0.46
- tfidf(offline,T2)=0.50*1.10=0.55
- tfidf(outage,T3)=0.50*1.10=0.55

**Managerial meaning:** “offline” and “outage” are rarer and therefore prioritized, despite fewer total mentions.

### Example 2: Customer Complaints (rare but critical)
**Table:**
| customer_id | complaint_text |
|---|---|
| C1 | "billing error refund" |
| C2 | "billing error" |
| C3 | "refund delayed" |
| C4 | "app crash" |
| C5 | "billing error" |

**Tokenization:**
- C1: billing, error, refund (len=3)
- C2: billing, error (len=2)
- C3: refund, delayed (len=2)
- C4: app, crash (len=2)
- C5: billing, error (len=2)

**TF:**
- tf(refund,C1)=1/3=0.33
- tf(crash,C4)=1/2=0.50

**DF:**
- df(billing)=3 (C1,C2,C5)
- df(refund)=2 (C1,C3)
- df(crash)=1 (C4)
- N=5

**IDF:**
- idf(billing)=log(6/4)=0.41
- idf(refund)=log(6/3)=0.69
- idf(crash)=log(6/2)=1.10

**TF‑IDF:**
- tfidf(refund,C1)=0.33*0.69=0.23
- tfidf(crash,C4)=0.50*1.10=0.55

**Managerial meaning:** “crash” becomes a high‑priority signal even with one complaint.

### Example 5: Supplier Delay Explanations (regex + TF‑IDF)
**Table:**
| supplier_id | comment |
|---|---|
| S1 | "delay 3 days due to customs" |
| S2 | "delay 2 days due to weather" |
| S3 | "delay 10 days due to customs" |
| S4 | "delay due to strike" |
| S5 | "delay 1 day due to weather" |

**Regex extraction:** extract number of days; tokenize reasons.
- Extracted days: 3,2,10, (missing),1
- Tokens for reasons: customs, weather, customs, strike, weather

**TF (reason tokens):**
- tf(customs,S1)=1/4=0.25 (delay, 3, days, customs)
- tf(strike,S4)=1/4=0.25

**DF:**
- df(customs)=2 (S1,S3)
- df(weather)=2 (S2,S5)
- df(strike)=1 (S4)
- N=5

**IDF:**
- idf(customs)=log(6/3)=0.69
- idf(strike)=log(6/2)=1.10

**TF‑IDF:**
- tfidf(strike,S4)=0.25*1.10=0.28
- tfidf(customs,S1)=0.25*0.69=0.17

**Managerial meaning:** “strike” is rare and should be escalated despite fewer mentions.

## 5. Operational Case Studies (minimum 5)

### Case 1: Call‑center issue prioritization
- **Question:** Which complaint type should be escalated today?
- **Method:** TF‑IDF on ticket notes; bigrams for negation (“not working”).
- **Failure at scale:** stop‑word skew overloads reducers; hot keys slow daily SLA dashboards.

### Case 2: Defect descriptions in manufacturing
- **Question:** Which defect words predict rework cost?
- **Method:** TF‑IDF on defect logs; rare terms flagged for investigation.
- **Failure at scale:** vocabulary explosion from serial numbers inflates memory and delays overnight batch.

### Case 3: Supplier delay explanations
- **Question:** Are delays mostly weather or customs?
- **Method:** Regex to extract reasons + TF‑IDF to spot rare causes.
- **Failure at scale:** unsafe regex stalls parsing; missing values spike.

### Case 4: Employee survey comments
- **Question:** What issues should HR address first?
- **Method:** TF‑IDF to highlight rare but severe sentiments; embeddings to cluster themes.
- **Failure at scale:** OOV rate increases with new jargon; cluster quality degrades.

### Case 5: Incident post‑mortems
- **Question:** Which outage patterns are repeating?
- **Method:** N‑grams capture patterns (“memory leak”, “db timeout”);
- **Failure at scale:** n‑gram vocabulary explodes; storage and shuffle costs increase.

## 6. Explicit Failure Modes (IEM framing)

| Failure mode | Symptom | Cost impact | Monitoring signal |
|---|---|---|---|
| Stop‑word skew | One reducer runs far longer | Longer batch window, SLA miss | max/median reducer load ratio |
| Vocabulary explosion | Feature table grows unexpectedly | Memory pressure, higher I/O | vocabulary size trend |
| Regex catastrophe | Single task stalls | Pipeline delays | regex timeout rate |
| OOV explosion | Model quality drops | Poor prioritization decisions | OOV rate trend |

## 8. Instructor Notes

### 90‑minute flow
1. **10 min:** operational framing + why text is process output
2. **25 min:** TF‑IDF with Example 1–3
3. **20 min:** n‑grams + Example 4
4. **15 min:** regex + embeddings (risk focus)
5. **10 min:** failure modes + dashboards
6. **10 min:** recap and exercises

### Common student mistakes
- Confusing TF with DF (local vs. global signals).
- Ignoring vocabulary growth when adding n‑grams.
- Treating regex as “free” without performance costs.

### Blackboard flow
1. Draw a small ticket table.
2. Compute TF, DF, IDF step‑by‑step.
3. Show TF‑IDF ranking and ask “what would you prioritize?”
4. Add a bigram example and discuss cost.
5. End with monitoring metrics that matter to managers.
